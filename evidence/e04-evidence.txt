MECHANISM
=========
New scripts/build-cross-module-gap-backlog.mjs parses E02's own
generated baseline (docs/programme/E02-MODULE-BASELINE.md, 46 modules
x 16 rows with evidence) and counts, per rubric row, how many modules
score <2 (a "gap"). A gap is "recurring" when it affects more than 50%
of the 46 scored modules.

The deliverable text names exactly 5 recurring gaps this phase must
route into shared work: "approvals, reversal, period close, bulk ops,
print" — 4 distinct rubric rows (reversal and period close are both
row 2, Lifecycle). Each is mapped to its shared-capability phase:
  Approvals  -> E05 (Approval-chain engine)
  Lifecycle  -> E06 (Reversal, correction and period close)
  CRUD depth -> E07 (Bulk operations framework)
  Documents  -> E30 (Print and export fidelity)
--check confirms both that each named row is real (measured against
E02's actual per-module scores, not assumed) and that its owner phase
is genuinely present in 14-TRACK-E-BUSINESS-APPS.md (a regex match on
"**E0N**", not a hardcoded assumption it exists).

Row 15 (Performance) is excluded from the entire gap analysis: it is
E01/E02's own documented MEASUREMENT gap (no module has recorded p95
data anywhere in this checkout), not a capability gap — counting it
here would manufacture a fake "100% of modules gap on Performance"
finding out of a tooling limitation already named elsewhere.

Any OTHER row the mechanical scan finds recurring, outside the named
4, is reported in the output (both --check's console NOTE and the
generated file's own section) but does NOT block the exit criterion —
E04 was scoped to the deliverable's own named list, not "resolve every
mechanically-detected pattern."
