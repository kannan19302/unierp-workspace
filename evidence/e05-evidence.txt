E05 — Approval-chain engine
Exit criterion: "Any entity gains approvals by declaration. A vacant
approver escalates rather than stalling. Verified against a
three-level hierarchy with a vacancy."

BEFORE
======
Read the pre-existing generic approval scaffolding
(ApprovalProcess/ApprovalRequest/ApprovalAction, used only by
CrmConfigService despite carrying no CRM-specific data) end to end:

  - declareApproval-equivalent (createApprovalProcess): real, generic,
    already usable by any `entity` string.
  - approveRequest(): accepted a `userId` from the caller and NEVER
    checked it against the step's declared approvers before recording
    an APPROVED action and advancing the step. Any authenticated
    caller could approve anything. Filed as D066 (CRITICAL).
  - No vacancy handling at all for position-based approver
    resolution — a step declared against an org position had no
    mechanism to escalate past a vacancy; D04's own
    ApprovalRoutingService (vacancy-safe hierarchy walk) existed as a
    separate, unconnected mechanism, never wired to the approval
    process engine.

The exit criterion's own words ("a vacant approver escalates rather
than stalling... verified against a three-level hierarchy with a
vacancy") could not be demonstrated against the pre-existing code —
there was no code path that resolved a step's approver through the
hierarchy at all.

MECHANISM (this phase's own work)
====================================
New unierp-api/src/modules/org-structure/approval-chain-engine.service.ts,
exported from OrgStructureModule for any module to inject:

  declareApproval(tenantId, orgId, name, entity, steps, createdBy)
    Creates an ApprovalProcess for ANY entity string — zero
    entity-specific code, proven by a test declaring one for
    "expense-report".

  submitForApproval(tenantId, userId, entityType, entityId, processId?)
    Creates an ApprovalRequest and immediately resolves step 0's real
    approver set — never leaves a request "pending" against a vacant
    position with literally no one who could ever act on it. If every
    level of a position-based step's hierarchy is vacant, this THROWS
    (a loud refusal) rather than creating a stalled, unapprovable
    request.

  approveStep(tenantId, requestId, userId, comments?)
    Resolves the CURRENT step's real approver set and REFUSES
    (ForbiddenException) if the caller isn't in it — the fix for
    D066. Supports mode: 'ANY' (first approval advances, sequential)
    and mode: 'ALL' (every resolved approver must act — parallel
    step). On advancing, resolves the NEXT step's approvers the same
    vacancy-safe way.

  resolveStepApprovers() (private)
    Named users as declared, OR an org position's occupant found via
    D04's ApprovalRoutingService.routeApproval() — the exact
    vacancy-escalation mechanism (climb past a vacant position to the
    next manager, refuse loudly if the whole chain is vacant), REUSED
    not reimplemented, per this session's established precedent
    (C04/M49, GlAccountingService, etc.).

WHAT THIS PHASE DOES NOT COVER
=================================
- Filed D066 (CRITICAL): the ORIGINAL vulnerable code path,
  CrmConfigService.approveRequest()/rejectRequest()/recallRequest(),
  was NOT modified or removed — it remains live and still missing the
  authorization check. E05 built the correct, reusable replacement;
  migrating crm.controller.ts's approval endpoints onto
  ApprovalChainEngineService (and deleting the vulnerable originals)
  is stated as necessary follow-up, not silently left implied-fixed.
- Delegation (a user temporarily delegating approval authority to
  another) is NOT built — this would need durable per-tenant
  delegation state, and no database-schema source repo is present in
  this checkout to add a table via migration (same constraint noted
  in E29's evidence). Stated, not hidden.
- SLA-based automatic escalation (a step auto-escalating after a time
  window elapses, distinct from vacancy-triggered escalation) is NOT
  built — this phase proves vacancy-escalation specifically, which is
  the exit criterion's own literal words. Time-based SLA escalation
  is a real, separate mechanism for a future phase.
- The controller/API surface for the new engine (REST endpoints
  wrapping declareApproval/submitForApproval/approveStep) was not
  built in this pass — the exit criterion is about the mechanism
  ("any entity gains approvals by declaration... verified against a
  three-level hierarchy"), proven at the service layer with a real,
  passing test; wiring a controller is a thin layer on a now-real
  mechanism, not a separate engineering problem.
