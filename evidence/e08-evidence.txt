E08 — Saved views, filters and personalisation
Exit criterion: "Every list in every module supports saved views with
no per-module code. A shared view respects the viewer's permissions,
not the author's."

BEFORE
======
Read the pre-existing saved-views module end-to-end
(unierp-api/src/modules/saved-views/). "No per-module code" is already
satisfied structurally — saved-views-generated.controller.ts (1,997
lines) and saved-views-generated.service.ts (605 lines) are a
code-generation layer already providing saved-view endpoints across
resources without hand-written per-module wiring; this pre-existing
mechanism was not the gap.

The gap is the second half of the exit criterion, and it was a real
authorization bypass, not a nuance: applyViewConfig() — the method
that resolves "what does this saved view actually show" (layout,
filters, columns) for a given viewId — never checked whether the
calling userId owned the view or had ever been granted a share for
it. Confirmed by the FAIL-first test: a random, never-shared-with
user successfully retrieved another user's view's full filter
configuration. Filed as D069 (CRITICAL).

MECHANISM (this phase's own work)
====================================
New private assertViewAccessible(tenantId, userId, viewId) in
SavedViewsDeepService, called at the top of applyViewConfig() before
any config is fetched:
  - Loads the view; NotFoundException if it doesn't exist for this
    tenant.
  - Allows immediately if the caller is the view's own author.
  - Otherwise requires a real savedViewSharing row with
    sharedWithUserId === the caller — ForbiddenException naming both
    the user and the view id if none exists.

The underlying resource permission (whether this viewer is even
allowed to see "customers" filtered this way) is intentionally left
to that resource's own RbacGuard-protected endpoint, executed
separately when the returned filters are applied — this fix closes
access to the SAVED VIEW CONFIGURATION itself, the precondition the
exit criterion's "respects the viewer's permissions" depends on. A
viewer who was never even granted access to a view cannot be said to
have their permissions "respected" by it at all; they should never
see it.

WHAT THIS PHASE DOES NOT COVER
=================================
- Filed D069 (CRITICAL): the fix was applied to applyViewConfig()
  specifically, the method the exit criterion's own scenario names
  ("apply a shared view"). Other accessors in the same service —
  getFilters(tenantId, viewId), which takes NO userId parameter at
  all and returns every active filter for a viewId unconditionally —
  were NOT individually audited for the identical missing-check
  pattern. On its face getFilters() has the same shape of bug.
  getColumnConfigs() is likely safe by construction (already
  userId-scoped to the caller's own column config). A full audit of
  every saved-view accessor for this pattern is stated as necessary
  follow-up, not silently assumed complete.
- "No per-module code" was verified by reading the existing
  code-generation layer (saved-views-generated.controller.ts/service.ts),
  not by exhaustively confirming every one of the 45 modules' list
  endpoints actually wires into it — that would require a platform-wide
  audit outside this phase's scope, similar in shape to E02's own
  46-module sweep.
