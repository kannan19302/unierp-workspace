THE BALANCE-CHECK INVESTIGATION
==================================
GlAccountingService.postJournalToBook() checked:
  Math.abs(totalDebit - totalCredit) > 0.01
on raw JavaScript floating-point numbers. Two real problems:
  1. Epsilon-tolerant: silently accepts ANY imbalance up to a full
     cent as "close enough" — double-entry requires EXACT equality,
     to the last minor unit, always.
  2. Float arithmetic on money, directly violating CODE_STANDARDS'
     own explicit rule.

The same file's OWN reverseJournalToBook()-adjacent parallel-book
check (elsewhere in the same 1,248-line file) already correctly used
Prisma.Decimal + .equals() — a live inconsistency within one file,
not a hypothetical.

MECHANISM (this phase's own fix)
====================================
postJournalToBook() now sums both totalDebit and totalCredit as
Prisma.Decimal (via .plus()) and requires exact .equals() — zero
tolerance, matching the correct pattern already present elsewhere in
the same file.

PROOF
=====
$ npx vitest run src/modules/advanced-finance/services/tests/gl-accounting-balance-check.service.spec.ts

Test 1 — "REFUSES a journal that is unbalanced by half a cent": a
100.00 debit vs 99.995 credit journal (genuinely, mathematically
unbalanced) is refused, naming both real totals in the error message.
FAILED against the pre-existing code before the fix (confirmed the
old code silently accepted it) — real FAIL-first proof, not assumed.

Test 2 — "ALLOWS a journal that is genuinely balanced, using exact
Decimal arithmetic": 0.1 + 0.2 debit vs 0.3 credit (NOT exactly equal
in IEEE 754 float — 0.1+0.2=0.30000000000000004) correctly posts,
proving the fix doesn't introduce a false-positive rejection of real
float-drift-adjacent but mathematically-equal currency amounts.
