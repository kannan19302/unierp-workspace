E13 — Fixed assets
Non-negotiables at exit: "Acquisition, depreciation schedules,
revaluation, impairment, insurance, transfer, disposal — every event
posting to the GL."

SCOPE NOTE
==========
E13's full scope (7 distinct event types, each required to post to the
GL) is far larger than this session's remaining budget. Investigated
depreciation directly (the exit criterion's second-named event, and
the one this service's own postDepreciation() most directly
implements) and found a real, critical bug on inspection: the GL
journal posting was CONDITIONAL on account mapping being complete,
while the domain event (reducing the asset's book value) was NOT -
meaning depreciation could silently proceed with real financial effect
and zero GL trace. Fixed it completely and correctly, and files the
honest remaining scope (the other 6 event types) rather than a
shallow pass across all of them.

THE INVESTIGATION
==================
Read fixed-assets.service.ts's postDepreciation() in full. Found:

  const assetAcc = asset.accountId || category?.assetAccountId;
  const accumAcc = asset.accumDepAccountId || category?.depreciationAccountId;
  const expenseAcc = category?.expenseAccountId;
  if (assetAcc && accumAcc && expenseAcc) {
    // ...create journal + 2 journalEntry rows...
  }
  // unconditionally, regardless of the above:
  const depRecord = await tx.assetDepreciation.create({ ..., status: "POSTED", journalId, ... });
  await tx.fixedAsset.update({ where: { id: assetId }, data: { currentValue: newBookValue, ... } });

journalId can be null (no journal branch taken) while the
assetDepreciation record is still marked POSTED and the asset's
currentValue is still permanently reduced.

THE BUG, CONFIRMED
====================
An asset (or its category) with incomplete GL account mapping - a
plausible real onboarding state, not a contrived edge case - had
postDepreciation() called against it. The call succeeded, returning a
depreciation record, reducing the asset's book value by the computed
depreciation amount, with NO GL journal ever created. The asset
register and the GL silently diverge from that point forward, with
nothing surfacing the gap.

MECHANISM (this phase's own fix)
====================================
The GL-account-mapping completeness check now runs BEFORE the
transaction opens and throws BadRequestException (naming the asset) if
any of the three required accounts (asset/accumulated-depreciation/
expense) is missing. Depreciation can no longer be posted at all - to
either the GL or the asset register - without a GL journal being
created in the same transaction as the depreciation record and the
book-value update.

WHAT THIS PHASE DOES NOT COVER — the honest, load-bearing gap
===================================================================
Filed as D088 (CRITICAL). Only postDepreciation() was audited and
fixed. NOT investigated in this pass:
  - transferAsset(), logMaintenance(), disposeAsset() in the same
    service - not checked for the same conditional-GL-skip pattern.
  - Revaluation and impairment - no dedicated method found in
    fixed-assets.service.ts; asset-lifecycle.service.ts and
    fixed-asset-deep.service.ts in advanced-finance/services/ are more
    likely candidates and were not opened in this pass.
  - Insurance - not searched for at all.
  - disposeAsset()'s own GL posting was read far enough to confirm its
    gainLoss calculation uses correct Prisma.Decimal arithmetic, but
    NOT far enough to confirm its GL journal creation is unconditional
    (vs. having the same optional-account-mapping pattern
    postDepreciation() had).
This defect's own discovery pattern - an optional GL-account check
silently degrading to "post the domain event, skip the GL journal" -
is filed as a plausible systemic pattern worth checking across the
other 6 named event types, and potentially other GL-posting services
outside fixed-assets entirely.
