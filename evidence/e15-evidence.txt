SCOPE NOTE
==========
E15's full scope covers the entire requisition-to-invoice chain with
approvals and partial receipts. Far larger than this session's
remaining budget. Investigated the phase's own most centrally-named
feature directly - "three-way match" - and found the single most
severe defect filed this session: not a subtle arithmetic bug, but a
completely fabricated report with zero connection to real invoice
data. Fixed it completely and correctly, and files the honest
remaining scope rather than a shallow pass across the rest of the
chain.

THE INVESTIGATION
==================
Read getThreeWayMatchReport() (procurement.service.ts) in full. Found:

  const invoicedQty = po.status === "RECEIVED" ? Number(poItem.quantity) : receivedQty;
  const orderedUnitPrice = Number(poItem.unitPrice);
  const invoicedUnitPrice = poId.endsWith("d") ? orderedUnitPrice * 1.1 : orderedUnitPrice;

No invoice model was ever queried. "invoicedQty" was assumed equal to
ordered quantity whenever the PO's own status happened to be
RECEIVED. "invoicedUnitPrice" was decided by whether the PO's cuid
string happens to end in the letter "d" - literally a coincidence of
ID generation, unrelated to any real invoiced price.

Confirmed the schema DOES provide a real mechanism for this:
APInvoiceCapture / APInvoiceCaptureLine, with matchingPurchaseOrderId
and matchingPOLineId fields specifically designed to join a captured
vendor invoice to a PO and PO line item. This model was never used by
getThreeWayMatchReport() at all.

THE BUG, CONFIRMED
====================
A purchase order could be reported "MATCHED" - the exact signal an AP
team would use to release payment - despite zero real invoice ever
having been captured or matched to it. The "invoice" side of the
three-way match was entirely simulated from the PO's own fields.

MECHANISM (this phase's own fix)
====================================
getThreeWayMatchReport() now queries real APInvoiceCapture records
(matchingPurchaseOrderId: poId, excluding REJECTED status), joins
their APInvoiceCaptureLine rows to PO line items via matchingPOLineId,
and computes invoicedQty (summed across matched lines) and
invoicedUnitPrice (quantity-weighted average, for the case of
multiple invoice lines matching one PO line) from real captured
invoice data. Each returned line item now reports hasInvoice: boolean;
qtyMatch/priceMatch can never be true without hasInvoice being true -
a PO with zero captured invoices can never be reported MATCHED.

WHAT THIS PHASE DOES NOT COVER — the honest, load-bearing gap
===================================================================
Filed as D090 (CRITICAL - the most severe finding this session; a
fabricated feature, not an arithmetic bug). Not investigated/resolved
in this pass:
  - The full requisition -> RFQ -> PO -> receipt chain with approvals
    and partial receipts - not re-verified; only the three-way-match
    report itself was audited.
  - The quantity-weighted-average approach for invoicedUnitPrice when
    multiple invoice lines match one PO line was not validated against
    any real AP reconciliation policy - whether a genuine price
    variance should itself trigger a discrepancy flag (vs. just
    averaging it away) is unresolved.
  - APInvoiceCapture.status values other than REJECTED (QUEUED, DRAFT,
    REVIEW_REQUIRED) are currently all treated as valid matches;
    whether an unreviewed capture should count toward a MATCHED result
    is a real AP-controls question not resolved here - plausibly only
    PROCESSED should count, a stricter default worth a follow-up
    decision.
  - This defect's own discovery pattern - a report/feature that looks
    complete (real endpoint, real DTOs, plausible function) but is
    entirely fabricated on close reading - is flagged as worth
    auditing across other "report"-shaped endpoints in the codebase,
    not just arithmetic bugs in otherwise-real logic (this session's
    other D084/D085/D086/D088/D089 pattern).
