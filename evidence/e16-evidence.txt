E16's full scope covers the entire quote-to-invoice chain plus

the first-named control mechanism in the exit criterion, and one this

allocation, returns, RMA) rather than a shallow pass across all of it.

THE INVESTIGATION
==================
Read sales.service.ts's B2B credit-limit check in createSalesOrder():
correctly computes initialStatus = "CREDIT_HOLD" when outstanding
balance + new order total exceeds the customer's credit limit. Found
a dedicated approveCreditHold() that re-validates so.status ===
"CREDIT_HOLD" before releasing.

Then read updateSalesOrderStatus() (the generic PATCH
/orders/:id/status handler) and found it accepts ANY status string
with zero transition validation:

  const updated = await prisma.salesOrder.update({
    where: { id }, data: { status },
  });

Checked sales.controller.ts's permission decorators:
  PATCH /orders/:id/status         -> @Permissions("sales.order.update")
  PATCH /orders/:id/approve-credit -> @Permissions("sales.order.update")

Both endpoints require the IDENTICAL permission - the "dedicated"
approval endpoint provides no additional authorization boundary.

THE BUG, CONFIRMED
====================
Calling updateSalesOrderStatus(tenantId, "so-1", "CONFIRMED") directly
on an order with status "CREDIT_HOLD" succeeded - the order was
confirmed with no rejection, completely bypassing approveCreditHold()
and the credit-limit gate the order was placed on hold for in the
first place.

MECHANISM (this phase's own fix)
====================================
updateSalesOrderStatus() now refuses any status transition AWAY from
"CREDIT_HOLD" through the generic path, throwing BadRequestException
that directs the caller to the dedicated approval endpoint. Only
approveCreditHold() can release a held order.
