decrement and finished-goods increment were two separate, unwrapped
top-level prisma calls inside one try/catch that only logs failures -
no prisma.$transaction anywhere.

THE BUG, CONFIRMED (Part 2, fixed)
====================================
If the finished-goods increment failed after raw-material decrements
had already committed (a plausible real DB failure mid-loop), the
warehouse would be left with materials silently vanished and no
finished goods produced - a permanent WIP integrity gap, logged but
never rolled back or surfaced.

MECHANISM (this phase's own fix, Part 2)
====================================
Both the raw-material consumption loop and the finished-goods
increment now run inside a single prisma.$transaction(), so a failure
anywhere rolls back everything written in that transaction so far.
Reorder-threshold checks (best-effort, may create a new PO) now run
AFTER the transaction commits, intentionally outside the atomicity
boundary since they're not part of WIP correctness.

PROOF
=====
$ npx vitest run src/modules/inventory/tests/inventory.event-handler.workorder-completed.spec.ts

Test 1 - "never commits a raw-material decrement if the finished-goods
production step fails - atomic via $transaction": simulates the tx
client's second upsert call failing, asserts prisma.$transaction was
called exactly once (proving atomicity is delegated to a real
transaction).
FAILED against the pre-existing code before the fix - confirmed
prisma.$transaction was called ZERO times (the old code used two
independent top-level calls). Real FAIL-first proof.

Test 2 - "performs raw-material consumption and finished-goods
production inside the same prisma.$transaction call": asserts both
writes ran through the same tx client in one $transaction call.
Also FAILED against the pre-existing code (same reason).

Both PASS after the fix.
