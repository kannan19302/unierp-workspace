THE INVESTIGATION
==================
Row 4 (Approvals) scored well on keyword/shape presence, but reading
WorkflowService.checkSlaBreaches() in full revealed the escalation
itself doesn't do anything real:

  const escalations = await prisma.workflowEscalationRule.findMany({ where: { slaRuleId: sla.id } });
  for (const esc of escalations) {
    await this.logAudit(tenantId, task.instanceId, task.id, "ESCALATED", "system",
      { escalationId: esc.id, escalateTo: esc.escalateToRole });
  }

No write to WorkflowTask.assigneeRole/assigneeId anywhere - the audit
log claims an escalation happened; the task's actual owner never
changes.

THE BUG, CONFIRMED
====================
A breached task (SLA limit 24h, created 48h ago) with a matching
escalation rule (escalateToRole: "MANAGER", escalateToUser: "user-
mgr-1") went through checkSlaBreaches(). An "ESCALATED" audit entry
was created, but prisma.workflowTask.update() was never called - the
task's assigneeRole/assigneeId remained whatever they were before the
breach.

MECHANISM (this phase's own fix)
====================================
checkSlaBreaches() now calls prisma.workflowTask.update() to set
assigneeRole/assigneeId to the escalation rule's escalateToRole/
escalateToUser, BEFORE logging the audit entry - the escalation
actually moves ownership.
