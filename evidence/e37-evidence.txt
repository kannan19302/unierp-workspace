E37 — Dashboards for end users
Deliverable: "Tenant-authored dashboards from governed metrics, with
drill-through to records."
Exit: "A dashboard tile drills through to the filtered record list
that produced it."

SCOPE NOTE
==========
Investigated the exit criterion's own named feature directly - drill-
through - and found the API endpoint a real tile click would call
(executeDrilldown) was completely fabricated: three hardcoded fake
rows returned unconditionally on every call, regardless of what
filter was requested. Fixed it to execute a real, filtered query
against the semantic layer, proved via break/restore, and files the
honest remaining scope (a sibling method with the same class of
fabrication, and unverified end-to-end UI wiring).

THE INVESTIGATION
==================
Read reporting-data-drilldown-deep.service.ts in full. Found:

  async executeDrilldown(tenantId, dto: {dimension, filterValue, metricKey}) {
    return {
      dimension: dto.dimension, filterValue: dto.filterValue, metricKey: dto.metricKey,
      results: [
        { label: "EMEA", value: 428500, growth: "+12.4%" },
        { label: "APAC", value: 312700, growth: "+8.1%" },
        { label: "Americas", value: 615200, growth: "+19.7%" },
      ],
      executedAt: new Date().toISOString(),
    };
  }

No database access anywhere - the three rows are literal, hardcoded,
and returned regardless of the actual dimension/filterValue/entity
requested. The sibling getDrilldownPaths() has the identical
fabrication pattern (two hardcoded path definitions).

THE BUG, CONFIRMED
====================
Clicking any dashboard tile, for any tenant, on any metric, would
show the IDENTICAL three fabricated regions with the identical
fabricated numbers - a drill-through that provably does not "drill
through to the filtered record list that produced it," since no
record list was ever consulted.

MECHANISM (this phase's own fix)
====================================
executeDrilldown() now requires an entity parameter (the semantic-
layer source the tile was built from) and executes a real query via
ReportingEngineService.executeQuery() with filters: { [dimension]:
filterValue } - reusing the exact infrastructure already proven
correct in E33/E35/E46 - returning the actual matching records.
Rejects with BadRequestException if no source entity is given.

WHAT THIS PHASE DOES NOT COVER — the honest, load-bearing gap
===================================================================

    drilldown-path definitions) - confirmed equally fabricated but
    not fixed; no DrilldownPath-style Prisma model exists to back a
    real implementation, requiring a schema migration (same
    constraint as D092/D095/D096/D100). Genuinely lower severity than

    endpoint itself correct but does not confirm end-to-end wiring
    from a rendered dashboard tile to this specific call.
