Deliverable: "Every user-facing string externalised; RTL; locale-
correct dates, numbers, currency, address formats and name ordering;
timezone correctness throughout."
Exit: "A hardcoded user-facing string fails CI. The platform is
fully usable in an RTL locale (G-15)."

SCOPE NOTE
==========
This phase's own exit criterion is unusually mechanical and directly
checkable: "A hardcoded user-facing string fails CI." A repo-wide
search confirmed this platform has ZERO i18n framework usage anywhere
across unierp-web's 994 .tsx files, ZERO RTL support, and the one real
backend translation service (I18nService) is unreachable via any HTTP
endpoint. Externalising 890+ pages' worth of hardcoded strings in one
pass is not attemptable. Built the real, literal mechanism this
phase's exit criterion names - a CI gate that fails on new hardcoded
strings - proved it via break/restore, and files the measured,
honest remaining scope (3,675 existing hardcoded strings) rather than
a shallow pass.

THE INVESTIGATION
==================
$ grep -rl "next-intl\|react-i18next" app/ --include=*.tsx
(zero matches across all 994 .tsx files under unierp-web/app)

$ grep -rln "dir=\"rtl\"\|direction.*rtl\|useDirection" app/ --include="*.tsx"
(zero matches)

$ grep -rln "I18nService" src --include="*.controller.ts"
(zero matches - I18nService exists with a real translate()/
getTranslations() implementation and a tenant-override mechanism, but
is not referenced by any controller anywhere)

Notably, I18nService.getSupportedLocales() already lists Arabic with
direction: "rtl" - RTL was at least designed for at the data-model
level, just never implemented anywhere in the frontend.

MECHANISM (this phase's own contribution)
====================================
scripts/check-hardcoded-strings.mjs: scans every .tsx file under
unierp-web/app for JSX text nodes matching
>[A-Za-z][A-Za-z ]{3,}< (4+ letters/spaces directly between two JSX
tag delimiters - catches literal text like >Create Band< without
matching JSX expression containers like >{value}<). Follows the same
baseline-ratchet pattern as every other gate this programme has built
(L02-L18): records the CURRENT count as a baseline and --check fails
only on a REGRESSION above it - never retroactively on already-
measured pre-existing debt.
