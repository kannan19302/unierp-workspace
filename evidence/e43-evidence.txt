E43 — Concurrency, optimistic locking and write idempotency
Deliverable: "A uniform concurrency contract: version columns on every
mutable entity, optimistic-lock conflict detection with a real
resolution UI, and idempotency keys required on every non-idempotent
write... this makes them mandatory and universal, not available."
Exit: "Two concurrent edits to one record produce a surfaced conflict,
never a silent last-write-wins. A double-submitted POST creates one
record - asserted by a test that fires the same request twice."

SCOPE NOTE
==========
This phase's own deliverable spans three large, independent
mechanisms (version columns everywhere, conflict-resolution UI,
mandatory idempotency). Investigated the third directly since existing
infrastructure (IdempotencyInterceptor, makeIdempotencyKey) already
exists per the phase brief itself - found it explicitly documented as
"opt-in," the exact opposite of "mandatory and universal." Built the
real enforcement mechanism, applied it to one genuinely double-submit-
sensitive endpoint as proof-of-technique, and files the honest
remaining scope (version columns, conflict-resolution UI, and the
other hundreds of unprotected mutating endpoints) rather than
attempting all three mechanisms shallowly.

THE INVESTIGATION
==================
Read idempotency.interceptor.ts's own docstring:
  "Opt-in per request... Requests without the header are untouched."

Confirmed: a mutating request (POST/PUT/PATCH/DELETE) with no
Idempotency-Key header - every existing caller in this codebase,
since nothing currently sends this header - passes straight through
with zero duplicate-write protection.

THE BUG, CONFIRMED
====================
A double-submitted POST /pos/orders (network retry, cashier double-
tap) creates TWO independent orders - exactly the failure mode this
phase's own exit criterion names as the thing that must never happen.

MECHANISM (this phase's own fix)
====================================
Rather than flipping the interceptor's global default (a sweeping,
unverifiable breaking change across every mutating route in a
~2,000-file API with 3 frontend clients), built a targeted
enforcement mechanism: new @RequireIdempotencyKey() decorator
(Reflector-based SetMetadata) that IdempotencyInterceptor now checks
via reflector.getAllAndOverride(). A mutating request with no header
to a decorated route is rejected with 400 IDEMPOTENCY_KEY_REQUIRED;
undecorated routes keep their existing opt-in behavior unchanged.
Applied to POST /pos/orders (createOrder) as proof of technique.
IdempotencyInterceptor now takes an optional Reflector; app.module.ts's
factory wiring updated to inject it.

PROOF
=====
$ npx vitest run src/common/idempotency/idempotency.interceptor.spec.ts

3 new tests:
  - "rejects a mutating request to a @RequireIdempotencyKey() route
    with no header": asserts the 400 rejection.
  - "does not reject a mutating request with no header on a route
    that has NOT opted in": positive-path regression, undecorated
    routes unaffected.
  - "a double-submitted POST with the same Idempotency-Key on a
    required route creates exactly one record": fires the same
    request twice through the interceptor with the same key+payload,
    asserts the underlying create-handler ran exactly once.

All 3 FAILED against the pre-existing code before adding the
enforcement check - confirmed a mutating request to a "required"
route with no header passed straight through with no rejection at
all. Real FAIL-first proof.
All 3 PASS after the fix. 12/12 tests in the file pass (9 pre-existing
+ 3 new).

WHAT THIS PHASE DOES NOT COVER — the honest, load-bearing gap
===================================================================
Filed as D102 (CRITICAL). This phase's own deliverable is much larger
than this pass:
  - Version columns on every mutable entity: the phase's own exit
    criterion states 36 entities carry a version column today, across
    only 3 of 18 schema files - the vast majority of mutable entities
    have none. Not touched in this pass.
  - Optimistic-lock conflict detection with a real resolution UI:
    "two concurrent edits produce a surfaced conflict, never silent
    last-write-wins" - not investigated; no such mechanism was
    located or built.
  - The idempotency-key REQUIREMENT itself is applied to exactly one
    endpoint (POST /pos/orders) as proof of technique. Every other
    mutating write in the codebase (sales orders, purchase orders,
    payments, invoices, and hundreds of other handlers) remains
    unprotected by default. A systematic audit identifying which
    endpoints are genuinely double-submit-sensitive, followed by
    applying the decorator across that set, is the real remaining
    scope.
