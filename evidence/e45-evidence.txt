E45 — AI model operations
Deliverable: "The local-first AI layer (modules/ai — 15 services,
Ollama, pgvector) given a lifecycle: model registry and pinned
versions, per-tenant model selection, prompt and template versioning,
cost and latency budgets, and graceful degradation when the model is
unavailable."
Exit: "A model version is pinned per tenant and an upgrade is a
deliberate, reversible act. An unavailable model degrades the
feature, never the request. Prompts are versioned artefacts, not
string literals in services."

SCOPE NOTE
==========
Investigated the exit criterion's first-named requirement directly -
"a model version is pinned per tenant" - and found it did not exist
at all, confirmed by AiConfigService's OWN comment stating "per-
tenant model override is explicitly out of scope." Built the real
mechanism, proved it via break/restore, and files the honest
remaining scope (graceful degradation was checked and found already
reasonably handled at its one call site; prompt versioning and
wiring the new pin into actual AI calls were not attempted).

THE INVESTIGATION
==================
Read ai-config.service.ts in full. Its own comment: "model and
baseUrl are always sourced live from AiService (env-configured),
never persisted - per-tenant model override is explicitly out of
scope." getConfig() always returned aiService.getDefaultModel() - a
single global env-configured model shared by every tenant, with no
pinning, no upgrade record, no rollback path.

Separately checked "an unavailable model degrades the feature, never
the request": found workflow-engine.service.ts's AI-review call site
already correctly guards with isConfigured() + try/catch defaulting
to safe values (ESCALATE to human review) on failure - a genuinely
good example, not a bug, not touched in this pass.

Also confirmed "prompts are versioned artefacts, not string
literals": workflow-engine.service.ts's own AI-review prompt is a raw
template string embedded directly in the service - still true, not
fixed in this pass.

THE BUG, CONFIRMED
====================
Changing OLLAMA_MODEL in the deployment environment silently changes
every tenant's AI behavior at once, with no per-tenant override, no
audit trail of when/whether any change happened - the exact opposite
of "a deliberate, reversible act."

MECHANISM (this phase's own fix)
====================================
AiConfig now includes pinnedModel: string | null. getConfig() returns
the tenant's pin when set, falling back to the deployment default -
using the same generic Setting.value JSON-blob pattern already
established for the enabled kill switch (no schema migration needed).
New setModel(tenantId, model) persists a pin (or null to explicitly
revert) and appends the change to an auditable modelPinHistory array
with a timestamp on the same setting row. New GET /ai/config/model/
history and POST /ai/config/model endpoints wire this to HTTP.
