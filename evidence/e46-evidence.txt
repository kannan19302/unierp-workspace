E46 — AI guardrails and provenance in a system of record
Deliverable: "Every AI-produced value is attributed, reviewable and
reversible: no AI write reaches a financial or clinical record
without an explicit human accept; retrieval is permission-scoped so
RAG cannot surface what the user may not read; every AI action is
audited with its inputs."
Exit: "An AI suggestion cannot post a journal entry or alter a
clinical note unaided. A RAG query provably cannot retrieve another
tenant's - or an unauthorised user's - documents. Every AI-derived
field is traceable to its prompt, model version and approver."

SCOPE NOTE
==========
Investigated the exit criterion's second-named requirement directly -
"a RAG query provably cannot retrieve another tenant's, or an
unauthorised user's, documents" - and found the "user" half of this
was completely unenforced: AiCopilotService.askData() was tenant-
scoped but had ZERO per-user permission scoping, letting any user
with the generic ai.create permission retrieve HR/payroll data via
natural language even without hr.employee.read. Fixed the concrete
finding, proved it via break/restore, and files the honest remaining
scope (financial/clinical write guardrails and prompt provenance were
checked but not fixed/built at scale).

THE INVESTIGATION
==================
Searched for AI services writing to journal entries or clinical
notes - found none (no AI service in the codebase currently posts
directly to either). Searched for a RAG/embedding implementation
(pgvector, mentioned in the module's own description) - found none
either, a separate total-absence finding not pursued further in this
pass since there's no RAG mechanism to guardrail yet.

Read AiCopilotService.askData() (the natural-language-to-report
feature) in full: receives only tenantId, executes a query against
the reporting engine's semantic layer, tenant-scoped by executeQuery.
Checked the semantic layer (reporting-engine.service.ts) - found an
"employees" entity exposing HR/payroll fields with NO access-control
metadata. Checked the controller: POST /ai/ask is gated only by the
generic ai.create permission, not anything entity-specific.

THE BUG, CONFIRMED
====================
A user holding only "ai.create" (no hr.employee.read) could ask the
AI copilot "what is the average salary in finance?" and receive a
real, accurate answer pulled straight from the Employee table -
completely bypassing the direct-access permission that would block
the same data through any other endpoint.

MECHANISM (this phase's own fix)
====================================
New ReportingSemanticEntity.requiredPermission?: string field.
employees entity marked requiredPermission: "hr.employee.read" (the
same permission real HR endpoints already require). askData() now
accepts the caller's permission array and, before executing any
query, checks whether the planned entity's requiredPermission is
held - throwing ForbiddenException before the query runs if not.
ai.controller.ts's askData handler threads req.user.permissions
through.

Note: deliberately used a local exact-match permission check rather
than @kannan19302/auth's own hasPermission (what RbacGuard uses) -
that package fails to resolve at all in this test environment
(confirmed: rbac.guard.spec.ts itself fails to collect for the
identical "Cannot find package '@unerp/shared'" reason, pre-existing
and documented throughout this session).

WHAT THIS PHASE DOES NOT COVER — the honest, load-bearing gap

  - Only the employees entity was marked permission-gated. The
    semantic layer's other entities (salesOrders, purchaseOrders,
    products, leads) were not individually reviewed for whether they
    also warrant a requiredPermission - employees was fixed as the
    single clearest, most sensitive example.
  - "No AI write reaches a financial or clinical record without an
    explicit human accept" - not investigated at scale; a targeted
    search found no AI service currently writes directly to journal
    entries or clinical notes, but this was not exhaustively verified
    across all 15 ai module services.
  - "Every AI-derived field is traceable to its prompt, model version
    and approver" - not investigated or built.
  - No RAG/embedding implementation (pgvector) was found anywhere in
    the codebase - a separate total-absence finding, not pursued
    further since there's no RAG mechanism yet to guardrail.
  - The local permission-check implementation could drift from
    RbacGuard's own (currently unreachable) wildcard-aware logic if
    that logic is ever extended - worth reconciling once the
    @kannan19302/auth package-resolution issue is fixed.
