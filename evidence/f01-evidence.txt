RLS-policied."
Exit: "check-rls-verify.mjs passes over every new table. A site

WHY THIS PHASE IS RELEASED RATHER THAN CLAIMED DONE
=====================================================
check-rls-verify.mjs's own real implementation
(unierp-data/scripts/check-rls-verify.mjs) requires a live
PostgreSQL connection (`DATABASE_URL`) to query actual RLS state via
PrismaClient - confirmed directly:

  $ cd unierp-data && node scripts/check-rls-verify.mjs
  PrismaClientInitializationError: Environment variable not found:
  DATABASE_URL.

This environment has none (the same class of blocker as E38/E44/
I11/J25/G05/H05/I04). A real, substantial fix WAS found, built, and
committed this pass (see below) - but "the exit criterion's own
command passes" could not be observed directly, so this is released
with the fix in place rather than falsely claimed finished.

THE INVESTIGATION
==================
Confirmed a real, mature multi-site builder data model already
exists (unierp-data/prisma/schema/web.prisma): WebSite,
WebSitePage, WebDomain, WebCollection, WebCollectionItem, WebMenu,
WebAsset, WebSeo, WebSettings, WebTemplate, WebChatbot,
WebFormSubmission, WebOrder, WebToLeadForm - covering most of the
deliverable's own named list (sites, pages, collections/entries,
menus, assets). "Sections" live as a JSON block-tree column on
WebPage/WebSitePage rather than a separate table (a real, deliberate
design choice, not a gap). "Locales" already exist as a separate,
already-RLS-covered model (confirmed via an earlier migration,
20260804010000). "Redirects" have no model anywhere - a genuine,
separate absence, filed below.

Checked whether these 14 tenant-scoped Web* tables actually have Row
Level Security, by searching every migration file this repository has
ever committed for their table names alongside the DDL that would
enable it:

  $ grep -rl "web_sites\|web_site_pages\|web_collections\|web_pages" \
    prisma/migrations --include=*.sql | xargs grep -l \
    "ENABLE ROW LEVEL SECURITY\|CREATE POLICY"
  (zero matches, on ANY of the 14 tables, ever)

THE BUG, CONFIRMED
====================
Every one of these 14 tables carries a `tenant_id` column - a
schema-declared tenant table, per check-rls-verify.mjs's own
schema-derived expected-set logic - but NONE of them ever had RLS
enabled or a tenant_isolation policy created. This is the identical
class of gap ARCHITECTURE_REVIEW section F5 and the
20260808010000_rls_camelcase_tenant_tables migration both already
name and fixed for a DIFFERENT set of 16 tables: a tenant table that
ships with RLS disabled is a tenant table any database session - not
just the application's own tenant-scoped middleware - can read or
write across every tenant's site content. This directly and severely
contradicts "a site provably cannot reference another tenant's
content": today, nothing at the database layer prevents it.

MECHANISM (this phase's fix)
====================================
Added prisma/migrations/20260812210000_rls_web_studio_sites/
migration.sql: enables RLS, forces it, and creates a
tenant_isolation_<table> policy for each of the 14 tables, following
the EXACT proven pattern already committed and (per this repo's own
history) presumably applied in 20260808010000 - the same
`DO $$ ... FOREACH t IN ARRAY ... EXECUTE format(...) ... END $$`
idempotent structure, adapted for these tables' snake_case tenant_id
column (the earlier migration's tables used camelCase tenantId).
`web_domains` is deliberately excluded - it has no direct tenant_id
column; its tenancy is derived through its owning WebSite by design,
not a gap.

VERIFICATION PERFORMED WITHOUT A LIVE DATABASE
==================================================
$ DATABASE_URL=<dummy> npx prisma validate --schema=prisma/schema
"The schemas at prisma\schema are valid" - confirms this migration's
existence does not break schema validation (though `validate` does
not parse or execute migration SQL itself - it validates the Prisma
schema files, a weaker but real check that nothing else regressed).

Manual review of the migration SQL: structurally identical to the
already-committed 20260808010000 migration (same DO $$ block shape,
same information_schema.tables existence guard, same idempotent
DROP POLICY IF EXISTS + CREATE POLICY pattern), with only the table
list and the tenant column name (tenant_id vs "tenantId") changed -
high confidence in correctness by direct structural analogy to a
pattern already proven to apply cleanly in this same repository, but
NOT independently executed or verified against a real database in
this pass.
