G02 — Permission and consent model for extensions
Deliverable: "Extensions declare required permissions; a tenant
admin sees them at install and consents; runtime grants can never
exceed the manifest."
Exit: "An extension attempting an undeclared operation is denied and
the attempt is audited. Escalating its own grants is impossible."

THE INVESTIGATION
==================
Read the real sandbox implementation (unierp-sandbox's
SandboxRunner.run(), the isolate-boundary host-capability bridge)
end to end against both halves of the exit criterion.

HALF 1 — "An extension attempting an undeclared operation is denied"
=========================================================================
VERDICT: real, confirmed, not fabricated. Every host-capability case
(log, dataRead, dataWrite, httpFetch, scheduleJob) calls
`requireScope(scope)` FIRST, which throws SandboxScopeError if the
installation's granted scopes don't include it - and this check runs
on the HOST side of the isolate boundary, re-checked at call time,
not trusted from anything the isolate itself asserts (the file's own
comment: "the bridge is the authority"). "Escalating its own grants
is impossible" is also real: `effectiveScopes()` (capabilities.ts)
computes the grant once at install time as an intersection of
(requested, installer's own permissions), and nothing in the sandbox
or extension-registry code re-reads or widens `grantedScopes` from
anywhere the extension itself could influence. Both halves of this
sentence hold up under inspection.

HALF 2 — "the attempt is audited"
=====================================
FOUND AND FIXED THIS PASS: a real but under-detailed audit trail.

A SandboxScopeError thrown host-side propagates up through
SandboxRunner.run()'s catch block unchanged (only a budget-error
regex match is special-cased there) to
ExtensionRegistryService.invoke()'s own catch block, which DOES call
recordUsage(...) - so a denial genuinely reaches
ExtensionInvocationUsage (now readable via this session's own G04
fix). But recordUsage() only ever stored `error.name` as errorKind -
literally the string "SandboxScopeError" for EVERY denial, regardless
of which capability was attempted. An auditor querying this table
could see "a scope violation happened, N times" but never WHICH
scope the extension tried to reach each time - the specific detail
that makes an audit record actionable ("this extension tried
http:fetch three times without the grant" vs. an undifferentiated
count).

The detail existed and was simply discarded: SandboxScopeError's own
constructor already builds a message string containing the exact
scope and extensionId - it just never exposed them as properties a
caller could read structurally instead of parsing a sentence.

MECHANISM (this phase's fix)
====================================
Added `readonly scope: Scope` and `readonly extensionId: string` as
real properties on SandboxScopeError (unierp-sandbox/src/index.ts),
alongside the existing message string. Bumped
@kannan19302/sandbox from 1.0.4 to 1.1.0.

Drafted the natural next step in unierp-api - having
recordUsage()'s errorKind read `SandboxScopeError:${error.scope}`
instead of the bare error name - and then REVERTED it: unierp-api's
installed dependency is still pinned to the PUBLISHED 1.0.4 (via
node_modules/.pnpm, not a workspace symlink, same situation as G01's
extension-api), which has no `scope` property, and referencing it
broke `tsc --noEmit` immediately with a real compile error
(TS2339). Confirmed the break, then reverted rather than ship
something that doesn't typecheck against what is actually installed.
