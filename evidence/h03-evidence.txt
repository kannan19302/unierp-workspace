H03 — Claim-verification gate
Deliverable: "A CI gate that fails when the marketing site asserts a
capability the platform does not have. Feature claims are declared
as data, checked against the platform's own capability manifest."
Exit: "Adding a feature claim with no corresponding capability entry
fails CI. This is the mechanism that prevents the site becoming
another @ts-nocheck-shaped lie."

THE INVESTIGATION
==================
Read app/(site)/features/FeaturesClient.tsx. Feature claims were
ALREADY declared as data (a MODULES array of 4 module groups, each
with a list of individual feature line items with per-plan
availability flags) rather than free prose - the deliverable's first
sentence was already true. But nothing checked that data against
anything real: `grep -n "capability.manifest\|check-feature-claims"`
across the whole repo returned zero matches before this pass -
exactly the gap this phase names, and this track's own 17-TRACK-H
doc explicitly cites it: "H03 (claim-verification gate) added because
this project has a documented history of claims outliving their
mechanisms."

MECHANISM (this phase's build)
====================================
Added capability-manifest.json: maps each of the 4 top-level MODULES
group names ("Finance & Accounting", "Human Resources", "CRM &
Sales", "Platform & Security") to the real unierp-api backend module
directories that back it (e.g. "Finance & Accounting" -> finance,
advanced-finance, fixed-assets - all three confirmed to exist via
`ls unierp-api/src/modules`).

Added scripts/ci/check-feature-claims.mjs: extracts the current
MODULES group names from FeaturesClient.tsx's own source, and for
each one checks (1) it has an entry in capability-manifest.json at
all, and (2) every backend directory that entry names actually
exists in unierp-api/src/modules. Fails loudly on either.

Wired into .github/workflows/guard.yml (this repo's existing "no code
with a failing check reaches the remote" gate), checking out
unierp-api as a sibling first - the same "the gate comes to the code"
pattern unierp-workspace's own policy-gate.yml uses for its
schema-aware checks (confirmed and reused this session already for
J11/D114's decimal-arithmetic ratchet fix).

PROOF (FAIL-first / break-restore, against the real gate)
==============================================================
$ node scripts/ci/check-feature-claims.mjs
(against the real, unmodified sibling unierp-api checkout)
"Claim-verification gate: 4 module-group claim(s), all mapped to
real, shipped backend modules." (exit 0)

Break 1 - a claim with no manifest entry: added a 5th MODULES group,
"Quantum Ledger Sync", with a made-up feature and no
capability-manifest.json entry.

  $ node scripts/ci/check-feature-claims.mjs
  FAILED: "Quantum Ledger Sync" is claimed in MODULES but has no
  entry in capability-manifest.json at all. (exit 1)

While proving this, found the FIRST version of the extraction regex
was fragile: it required the `name:` field to be the LITERAL next
line after the opening brace, so inserting a one-line comment between
them silently made the new claim invisible to the gate (it reported
"0 failures" even with the fake claim present). Fixed the extraction
to search a small lookahead window rather than the single next line,
then re-confirmed the SAME fake claim, now WITH a comment between the
brace and the name field, is still caught:

  $ node scripts/ci/check-feature-claims.mjs
  FAILED: "Quantum Ledger Sync" is claimed in MODULES but has no
  entry in capability-manifest.json at all. (exit 1, with the
  comment present)

Restored FeaturesClient.tsx to its original content (confirmed via
`git status --short` showing zero diff for that file).

Break 2 - a manifest entry naming a nonexistent backend directory:
temporarily added "nonexistent-module-for-break-proof" to "CRM &
Sales"'s manifest entry.

  $ node scripts/ci/check-feature-claims.mjs
  FAILED: "CRM & Sales" maps to backend module dir(s) that do not
  exist in unierp-api/src/modules: nonexistent-module-for-break-proof.
  (exit 1)

Restored the manifest entry.

Final state:
  $ node scripts/ci/check-feature-claims.mjs
  Claim-verification gate: 4 module-group claim(s), all mapped to
  real, shipped backend modules. (exit 0)

WHAT THIS PHASE DOES NOT COVER — the honest, load-bearing gap
===================================================================
Filed as D132 (CRITICAL). Not fixed in this pass:
  - Deliberately scoped to the ~4 top-level module-GROUP claims, not
    every one of the ~40 individual feature line items inside them
    (e.g. "General Ledger", "2FA / Authenticator App"). Mapping every
    one of those to a specific, verifiable backend endpoint or
    service method is a much larger effort - this pass verifies "this
    module group is a real, shipped module," not "every individual
    line item under it is independently proven real."
  - Only the /features page's MODULES data was covered. Other pages
    (home, pricing, about) may make feature claims in free prose, not
    as structured data - this gate cannot check those, and the
    deliverable's "declared as data" premise does not yet hold for
    the rest of the site.
  - The gate's real-directory check only confirms a backend module
    DIRECTORY exists - it does not verify the specific claimed
    feature (e.g. "IFRS & GAAP Compliance") is actually implemented
    inside that module, only that the module itself is real. A
    directory existing with unrelated or incomplete contents would
    still pass.
