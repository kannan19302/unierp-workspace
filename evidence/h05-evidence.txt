H05 — Pricing, plans and comparison
Deliverable: "Pricing page driven by the SAME plan definitions the
platform bills from, so published prices cannot drift from what is
charged."
Exit: "A plan change in C13 updates the pricing page without an
edit. A mismatch fails CI."

WHY THIS PHASE IS RELEASED RATHER THAN CLAIMED DONE
=====================================================
Investigated this deliverable's own named concern directly - does the
public pricing page reflect the same data the platform actually
bills from - and confirmed it does not, at all, today.

THE INVESTIGATION
==================
Found C13's real, mature billing-plan model in the Prisma schema:
  - SaaSPlan (name, maxUsers, maxStorage, maxApiCalls, features JSON,
    isPublic, sortOrder, status, version, supersededBy - real
    plan-versioning support)
  - SaaSPlanPrice (planId, currency, region, monthly/yearly Decimal
    prices, stripePriceId - real, currency/region-aware pricing)
  - TenantSubscription linking a real tenant to a real plan

Confirmed unierp-api exposes this via GET /saas/plans
(SaasController.getPlans(), gated by "saas.read" - a real, structured
endpoint backed by this real data, not fabricated).

Then read app/(site)/pricing/page.tsx in unierp-corporate-website (a
SEPARATE repository, the public marketing site) and found:

  const PLANS = [
    { name: 'Starter', ... },
    { name: 'Professional', ... },
    { name: 'Enterprise', ... },
  ];

100% hardcoded static data, embedded directly in the page's source
code. Zero connection to SaaSPlan/SaaSPlanPrice, zero API call to
GET /saas/plans or anything else, anywhere in this file or its
imports.

THE BUG, CONFIRMED
====================
This directly and completely violates the exit criterion: "a plan
change in C13 updates the pricing page without an edit" is false
today - changing a SaaSPlanPrice row's monthly/yearly value would
never reach the public pricing page at all, since nothing on that
page ever reads it. The two systems (what UniERP actually charges,
and what the marketing site claims it charges) can drift apart
silently and indefinitely, with nothing to catch it - exactly the
"published prices cannot drift from what is charged" guarantee this
phase exists to build, currently entirely absent.

WHY THIS CANNOT BE FULLY BUILT AND PROVEN HERE
==================================================
Closing this gap for real requires the pricing page to fetch live
plan/price data - either at build time (a data-fetching step calling
a live unierp-api instance) or at request time (a live cross-origin
API call from the deployed site). Either path needs:
  1. A running unierp-api instance reachable from this build/runtime.
  2. A live PostgreSQL database with real SaaSPlan/SaaSPlanPrice rows
     to fetch and display.
Neither exists in this environment (no DATABASE_URL, confirmed
repeatedly this session: E38, E44, I11, J25, G05). Even a from-scratch
integration could not be demonstrably proven - "a plan change updates
the page without an edit" requires actually changing a real price row
and observing the page reflect it, which needs both live endpoints.

This is a different shape of gap than H03 (which needed only a
directory-existence check, satisfiable with two local repo checkouts
and no live database) - H05's exit criterion is about live DATA
values (prices), not static structural facts (does a directory
exist), and prices only exist in a live database.

WHAT WOULD BE NEEDED TO ACTUALLY CLOSE THIS PHASE
====================================================
1. A provisioned unierp-api instance + PostgreSQL database with real,
   seeded SaaSPlan/SaaSPlanPrice rows representing the actual public
   plans.
2. A build-time or request-time data fetch in
   app/(site)/pricing/page.tsx replacing the hardcoded PLANS array,
   calling GET /saas/plans (or a purpose-built public, unauthenticated
   pricing endpoint, since GET /saas/plans currently requires
   "saas.read" and the marketing site has no authenticated session -
   worth checking whether that permission gate is appropriate for a
   PUBLIC pricing page or whether a separate public endpoint is
   needed).
3. A CI gate (once both of the above exist) that fetches the live
   plan data and fails if the deployed page's rendered prices diverge
   from it - the actual "a mismatch fails CI" mechanism this phase's
   exit criterion names.
