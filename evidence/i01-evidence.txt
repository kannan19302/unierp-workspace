THE INVESTIGATION — CI half
===============================
Read unierp-workspace/.github/workflows/mobile-ci.yml (the workflow
this phase's own deliverable names) and found it filtered on
`apps/mobile/**` and ran every job with
`working-directory: apps/mobile` - a monorepo path. unierp-mobile is
its own top-level repository (lib/, test/, android/, ios/, windows/
all live at ITS OWN root) - `apps/mobile` has not existed anywhere in
this repo since the platform split into 30 repositories. This
workflow could never have fired correctly for the repo it exists to
protect.

Then checked whether unierp-mobile's own CI even calls this workflow:

  $ cat unierp-mobile/.github/workflows/ci.yml
  jobs:
    ci:
      uses: kannan19302/unierp-workspace/.github/workflows/reusable-ci.yml@main

It called the GENERIC, Node/pnpm-oriented `reusable-ci.yml` instead -
never `mobile-ci.yml` at all. Confirmed unierp-mobile has no
package.json anywhere:

  $ ls unierp-mobile/package.json
  No such file or directory

`reusable-ci.yml`'s `pnpm install --frozen-lockfile` /
`pnpm run build/lint/test` steps have nothing to act on in a repo
with no package.json. This Flutter client had no real CI coverage of
any kind from either angle: the workflow NAMED for it
(`mobile-ci.yml`) was never called, and the workflow that WAS called
does nothing meaningful for a Dart/Flutter project.

MECHANISM (this phase's fix)
====================================
Converted `mobile-ci.yml` to a reusable `workflow_call` workflow
(the same pattern every other repo's `ci.yml` already uses to call
into unierp-workspace) and removed the stale `apps/mobile` path
prefix from every job, so `analyze`/`build-android`/`build-windows`/
`build-ios` all run against the repo root they are actually checked
out to. Updated `unierp-mobile/.github/workflows/ci.yml` to call this
fixed workflow instead of the ill-fitting `reusable-ci.yml`.
