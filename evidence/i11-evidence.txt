I11 — Mobile security
Deliverable: "Biometric unlock, secure storage, certificate pinning,
jailbreak/root detection, screenshot policy, remote wipe, and
enforced session policy."
Exit: "A tenant's MFA and session policy are enforced on mobile
identically to web. Credentials are provably not in plain storage."

WHY THIS PHASE IS RELEASED RATHER THAN CLAIMED DONE
=====================================================
This environment has no Flutter/Dart SDK installed (confirmed:
`which flutter dart` finds neither; `flutter --version` reports
"command not found"). unierp-mobile is a Flutter app — every one of
this deliverable's seven items requires writing and, per this
programme's own protocol, PROVING Dart source via a real
`flutter test` run (FAIL-first, then PASS, then break/restore). None
of that is executable without the SDK, and installing a full Flutter
toolchain (Android/iOS build chains included) is outside what this
session can provision. This is the same class of environment
blocker as E44/E38 (a live PostgreSQL instance), just for a different
piece of infrastructure — a real one, not a shortcut to avoid the
work.

Unlike E44/E38, this investigation could still be done in full via
static source and dependency inspection, which is real, mechanical,
and directly answers the exit criterion's first sentence ("Credentials
are provably not in plain storage" is answerable by reading the
storage code; it does not require running it).

THE INVESTIGATION — one item at a time
========================================

1. SECURE STORAGE — lib/core/storage/secure_session_store.dart
   Real. Access token, user, tenant, and permissions are written via
   `flutter_secure_storage` (`AndroidOptions(encryptedSharedPreferences:
   true)`, `IOSOptions(accessibility:
   KeychainAccessibility.first_unlock_this_device)`) - Keychain on iOS,
   EncryptedSharedPreferences on Android. The refresh token is
   deliberately never stored here at all - it stays an httpOnly cookie
   managed by `CookieStore`, mirroring web's own pattern (the file's own
   comment cites `sealSessionCookies` in
   `apps/api/src/modules/auth/auth.controller.ts`). `clear()` wipes
   every artefact on logout/dead-refresh.
   VERDICT: adequate. Credentials are provably not in plain storage,
   confirmed by reading the actual storage backend used, not by a
   comment claiming it.

2. BIOMETRIC UNLOCK — FABRICATED, confirmed
   `SecureSessionStore` has `readBiometricEnabled()` /
   `writeBiometricEnabled()`, backed by a real secure-storage-persisted
   flag. But:
     $ grep -rln "readBiometricEnabled\|writeBiometricEnabled\|local_auth\|LocalAuthentication" lib --include=*.dart
     lib/core/storage/secure_session_store.dart   (only the definition)
   NEITHER method is called from anywhere else in the app. The
   `local_auth` package (the standard Flutter biometric-prompt plugin)
   is not even a pubspec.yaml dependency:
     $ grep -n "local_auth\|biometric" pubspec.yaml
     (no matches)
   There is a stored preference that, if set, is never read to gate
   anything, and no biometric prompt exists anywhere in the codebase.
   This is the exact "looks implemented, does nothing" fabrication
   pattern this session has repeatedly found elsewhere (D090/D098/
   D108/D110) - a well-named getter/setter pair standing in for a
   feature that was never built.

3. CERTIFICATE PINNING — ABSENT, confirmed
     $ grep -rln "certificate_pinning\|http_certificate_pinning\|sslPinning" lib pubspec.yaml
     (no matches)
   No pinning package, no manual `BadCertificateCallback`/pin-set
   verification anywhere. `dio` (the HTTP client used, confirmed in
   pubspec.yaml) trusts the platform's default certificate store with
   no additional pinning layer.

4. JAILBREAK/ROOT DETECTION — ABSENT, confirmed
     $ grep -rln "jailbreak_root_detection\|flutter_jailbreak_detection\|freerasp\|talsec" lib pubspec.yaml
     (no matches)
   No jailbreak/root-detection package or custom check exists anywhere.

5. SCREENSHOT POLICY — ABSENT, confirmed
     $ grep -rln "FLAG_SECURE\|screenshot" lib pubspec.yaml android/app/src ios/Runner
     (no matches)
   No `FLAG_SECURE` set on Android, no `UIScreen` capture-protection on
   iOS, no in-app screenshot-block package.

6. REMOTE WIPE — ABSENT, confirmed
     $ grep -rln "remote.wipe\|remoteWipe\|deviceWipe" lib
     (no matches)
   No remote-wipe mechanism exists - a lost/stolen device with a valid
   session cannot be remotely invalidated from any admin surface this
   repo controls, beyond the token's own natural expiry (whatever that
   turns out to be - see item 7).

7. SESSION POLICY PARITY WITH WEB — partially inspected, NOT verifiable
   without running the app
   `lib/core/network/interceptors/jwt_auth_interceptor.dart` and
   `auth_interceptor.dart` implement real single-flight token-refresh
   locking and 401-triggered request queuing - the mechanics look
   deliberately built, not fabricated. But whether the access-token
   lifetime, MFA step-up requirements, and idle-timeout policy actually
   MATCH web's (H04's own review this session found web's admin session
   is an 8h JWT with no revocation) could not be confirmed without
   running both clients side by side - static reading of the
   interceptor code does not reveal the token's configured TTL or
   whether MFA is enforced identically on mobile's login flow.
   VERDICT: not established either way; filed as unverified, not as
   passing.

WHAT WOULD BE NEEDED TO ACTUALLY CLOSE THIS PHASE
====================================================
1. A Flutter SDK installation (Android/iOS toolchains) in the working
   environment, to write, run, and break/restore-prove Dart tests for
   each of the six unbuilt/unverified items.
2. Add the `local_auth` package and wire `readBiometricEnabled()` to
   an actual prompt gating app resume/launch - the most tractable of
   the six, since the storage flag and secure-storage foundation
   already exist.
3. Add a certificate-pinning layer to the `dio` client configuration.
4. Add a jailbreak/root-detection package and a documented policy for
   what happens when it fires (block, warn, degrade).
5. Set `FLAG_SECURE` (Android) and the iOS screen-capture-protection
   equivalent.
6. Design and build a remote-wipe mechanism, almost certainly
   server-driven (an admin-triggered session/device invalidation that
   the mobile client checks for and acts on).
7. Run both web and mobile login/session flows side by side to confirm
   MFA and session-policy parity, which requires a running backend and
   both clients.

None of these seven are attemptable without a Flutter SDK and,for
items 6-7, a running backend - the same "genuine infrastructure this
environment does not provide" shape as E44/E38, not a shortcut.
