THE INVESTIGATION
==================
Read scripts/ci/cdc-harness.mjs - a real, sophisticated, already-
built mechanism (M2, PLATFORM_ARCHITECTURE.md § 4.5): consumers
publish a machine-readable record of every symbol they import from
each `@kannan19302/*` provider (cdc/expectations.json), and this
harness recomputes that corpus and replays it against each
provider's actual current exported surface, failing loudly on any
symbol a consumer expects that a provider no longer exports.

Ran it:
  $ node scripts/ci/cdc-harness.mjs
  Error: Cannot find module 'typescript'

No `typescript` dependency, no package.json, in this repo at all.
Installed it (typescript@5.9.3, matching the version used elsewhere
in this session's own work) and ran it again - it silently reported
finding ZERO providers and ZERO consumers doing any real checking,
because PROVIDERS/CONSUMERS in the script named MONOREPO paths
(`apps/web`, `packages/sdk`) - and this repository's own `apps/` and
`packages/` directories are empty:

  $ ls apps packages
  (empty / packages/database only, itself empty)

The script's own docstring explains why: it was built BEFORE "the
Phase 3 split" of this platform into 30 separate repositories, and
was never updated for the split it names. Confirmed via grep across
every `.github/workflows/*.yml` in this entire polyrepo (30 repos):

  $ grep -rln "cdc-harness" */.github/workflows/*.yml
  (zero matches, anywhere)

A real mechanism, built, never connected to the polyrepo it now runs
against, and never wired into any CI workflow. This directly and
completely violates the exit criterion: a provider change breaking a
consumer expectation currently fails NOTHING, because the check that
would catch it either finds nothing to check (if run at all) or is
never run in the first place.

WHAT THIS PHASE DOES NOT COVER — the honest, load-bearing gap
===================================================================
Filed as D136 (CRITICAL). Not fixed in this pass:

    cdc-gate.yml, as the concrete, proven example. The other 9
    providers (unierp-contracts, unierp-kernel, unierp-sdk,
    unierp-extension-api, unierp-sandbox, unierp-framework,
    unierp-data, unierp-shared, unierp-auth) do not yet call it -
    each needs the same one-line addition to its own ci.yml, not
    done here for all 9 in this pass.
  - The `@kannan19302/database` provider surface remains "open"
    (not fully enumerable by this harness - a pre-existing,
    documented limitation of the harness's own re-export-following
    logic, not something this pass changed or investigated further)
    - misses against it are warnings, not hard failures.
  - The reusable workflow was authored and reviewed but not run in
    a real GitHub Actions environment (this session has no way to
    trigger a live CI run) - correctness was validated by running
    the exact same script it calls locally against the exact same
    real repo checkouts, which is a strong but not identical proof
    to an actual CI execution.
