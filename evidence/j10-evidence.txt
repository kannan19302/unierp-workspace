INVARIANT 1 — "a ledger always balances"
============================================
Installed fast-check as a dev dependency (not present anywhere in
this repo before this phase). Investigated
GlAccountingService.createJournal() (src/modules/advanced-finance/
services/gl-accounting.service.ts), the sibling of
postJournalToBook() - which this session's own earlier phase (E09)
already fixed for the identical bug class, confirmed via the existing
gl-accounting-balance-check.service.spec.ts test file citing that
history directly.

createJournal() still had the ORIGINAL bug:

  const debits = dto.entries.reduce((sum, e) => sum + e.debit, 0);
  const credits = dto.entries.reduce((sum, e) => sum + e.credit, 0);
  if (Math.abs(debits - credits) > 0.01) throw ...

This is not float-summation drift - it is a designed epsilon
tolerance that accepts ANY imbalance up to a full cent as "close
enough." Wrote a fast-check property searching the input space for
genuinely unbalanced [debit, credit] pairs (a real Decimal(19,4)
discrepancy strictly greater than zero and at most one cent) that
this check wrongly accepts as balanced.

THE EDGE CASE FOUND (recorded)
==================================
Within 500 generated runs (seed 42, reproducible), fast-check found
and the test records:

  [1, 0.00009999999747378752]

i.e. a debit of 1.0000 against a credit of ~0.9999 - a real,
Decimal(19,4)-precision discrepancy of one hundredth of a cent to a
tenth of a cent - accepted as "balanced" by the original check. This
directly and provably violates "a ledger always balances": real,
wrong money would be posted.

MECHANISM (this phase's fix)
====================================
Fixed createJournal() to use exact Prisma.Decimal arithmetic
(sum.add(new Prisma.Decimal(e.debit)) accumulation, compared via
.equals()), matching the sibling postJournalToBook() fix exactly -
not a new, independently-drifting mechanism.
