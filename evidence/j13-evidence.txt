Deliverable: "Declared budgets for API p95 and page load, enforced
in CI on a representative dataset."
Exit: "A regression beyond budget fails the build. Budgets are
declared as data, not measured ad hoc (G-17)."

WHY THIS PHASE IS RELEASED RATHER THAN CLAIMED DONE
=====================================================
Investigated the exit criterion's own named mechanism directly: does
a regression beyond budget fail the build today. Found
.github/workflows/load-test.yml (a real, previously-built k6 CI
workflow) referencing six scenario files under
load-tests/scenarios/. Checked whether that directory, or any of
those files, exists anywhere in this repository:

  $ find . -iname "load-tests"
  (zero matches, anywhere)

The directory this workflow has referenced since it was written has
never existed. Every job in load-test.yml would fail immediately on
a missing-file error if it ever ran. Separately confirmed the
workflow's own triggers:

  on:
    schedule:
      - cron: '0 2 * * *'
    workflow_dispatch:

Never `push`/`pull_request` - so even if the scenario files existed
and passed, this workflow could never "fail the build" in the sense
the exit criterion means (a PR check blocking a merge). And
`grep -l "thresholds"` across every JS file this repo has ever had
under any load-testing path returns nothing - no k6 threshold (the
actual mechanism that turns a budget into a real pass/fail signal)
had ever been declared anywhere. Zero budgets existed as data; zero
mechanism existed to fail a build on a regression.

MECHANISM (this phase's build)
====================================
Added load-tests/budgets.json - real, named performance budgets
(API p95 targets for health/auth/list/document-post routes, page
load targets for the dashboard and marketing home pages) declared as
data, per G-17's own wording, not scattered ad hoc through scripts.

Added two of the six scenario files load-test.yml already
references: smoke-test.js (a basic health-check budget) and
list-paginate.js (a representative "API p95" tenant-scoped paginated
list endpoint - the classic p95-sensitive shape: large tables, N+1
risk, missing indexes). Both import budgets.json and turn the
relevant entry into a genuine k6 `thresholds` block
(`http_req_duration: [p(95)<Nms]`, `http_req_failed: [rate<X]`) -
this is k6's own real mechanism for making a run exit non-zero when
a budget is exceeded, not a custom re-implementation.

Both syntactically valid JavaScript (no output = clean).

Not verified: neither script has been EXECUTED - this environment

k6 API usage (verified against k6's own public documentation
structure, not by running it), but genuine execution-level proof
(the script actually runs, actually measures p95, actually exits
non-zero on a seeded regression) could not be produced here.
