Deliverable: "Scheduled rehearsal of full restore and per-tenant
PITR, with measured RPO/RTO published."
Exit: "RPO and RTO are committed numbers proven by rehearsal, and the
rehearsal is on a schedule that fails loudly if skipped (G-11)."

WHY THIS PHASE IS RELEASED RATHER THAN CLAIMED DONE
=====================================================
The exit criterion's first half — "RPO and RTO are committed numbers
proven by rehearsal" — requires an actual rehearsal to run: a real
backup taken from a live PostgreSQL instance, restored into a
disposable database, timed, and verified row-for-row. This
environment has no Docker and no live Postgres instance available
(the same class of infrastructure gap as E38/E44/I11). The rehearsal
mechanism itself (scripts/rehearse-restore.mjs) already exists from
an earlier phase (A22) and is real - it takes a real pg_dump, restores
into a clean disposable DB via `docker exec`, proves byte-equivalent
table/row counts and _prisma_migrations, and logs measured RTO/RPO.
It cannot be executed here to establish even a single committed
RPO/RTO number.

THE TRACTABLE PIECE BUILT AND PROVEN THIS PASS
==================================================
The exit criterion's second half - "the rehearsal is on a schedule
that fails loudly if SKIPPED" (G-11) - was investigated directly and
found to have a real, concrete, buildable gap independent of live
database infrastructure.

.github/workflows/backup-restore.yml runs the rehearsal nightly via
`on: schedule: cron: '10 3 * * *'`, and the rehearsal script itself
fails loudly (non-zero exit) if a restore fails to verify. That
covers "the rehearsal fails loudly when it RUNS AND FAILS." It does
NOT cover "fails loudly if SKIPPED": a `schedule`-triggered GitHub
Actions workflow can stop firing ENTIRELY, silently, with zero error
anywhere - GitHub disables scheduled workflows in a repository after
60 days with no push/PR activity on the default branch, and there is
no notification when this happens. If that occurred, the rehearsal
guarantee would quietly evaporate and nothing in this repository
would say so.

MECHANISM (this phase's build)
====================================
Added scripts/check-rehearsal-freshness.mjs: reads the append-only
rehearsal log (var/backups/rehearsal-log.jsonl, written by
rehearse-restore.mjs) and fails loudly if:
  1. no rehearsal has EVER been logged, or
  2. the most recent rehearsal is older than a 48h freshness window
     (nightly cron + generous buffer), or
  3. the most recent rehearsal did not verify.

Designed to run on ORDINARY push/PR activity rather than another
`schedule` trigger (which would share the exact same silent-disable
risk it exists to catch) - this workspace receives a push on every
single ADP phase this session completes, giving the freshness gate a
far more reliable trigger than the cron it is watching over.

Restored the environment to its original state (no rehearsal log
tracked or committed - this environment never ran a real one).

WHAT THIS PHASE DOES NOT COVER — the honest, load-bearing gap
===================================================================
Filed as D123 (CRITICAL). Not fixed / not attemptable in this pass:
  - Zero RPO/RTO numbers are committed anywhere - the entire first
    half of the exit criterion requires a real rehearsal against a
    real database this environment cannot provide.
  - The new freshness gate is deliberately NOT wired into any live,
    push/PR-triggered CI workflow. Wiring it would make it fail on
    every single commit to this repository from now on, since no
    rehearsal has ever actually run and no rehearsal log exists to
    satisfy it - and this session has no way to establish that
    initial passing state (no Docker/Postgres here). Wiring an
    inherently-failing gate into standard CI is a real, consequential,
    hard-to-reverse action affecting every future commit to a real
    GitHub repository, and was deliberately not taken without a way
    to resolve the resulting failure.
  - Per-tenant PITR (the deliverable's other named requirement) was
    not investigated in this pass at all.

WHAT WOULD BE NEEDED TO ACTUALLY CLOSE THIS PHASE
