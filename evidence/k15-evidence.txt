K15 — Data portability and exit rights
Deliverable: "A contractual, tested exit path: complete export,
assisted migration away, deletion certificate - the honest
counterpart to the self-hosting promise."
Exit: "A tenant exits fully unaided and receives a deletion
certificate. Verified by rehearsal, not by clause (G-4)."

THE INVESTIGATION
==================
Investigated the exit criterion's own named artefact directly: the
deletion certificate. Found TenantExportOffboardingService.
offboardTenant() (src/platform/v1/tenant-export-offboarding.service.ts),
reachable via POST /:tenantId/offboard (gated by
"system.offboarding.write" AND two-person control).

The method:
  1. Sets tenant.status = 'OFFBOARDED'.
  2. Cancels active subscriptions.
  3. Creates a DataExportJob row with status 'PROCESSING' (never
     itself processed by this method or, confirmed by grep, by
     ANY worker/cron anywhere in this codebase).
  4. Cryptographically signs (HMAC-SHA256) and returns an artefact
     literally TYPED "DELETION_CERTIFICATE" with a `deletedAt`
     timestamp - claiming, with a signature meant to look tamper-
     evident and legally significant, that tenant data was deleted.

THE BUG, CONFIRMED
====================
No tenant data is deleted anywhere in this method, or subsequently:

  $ grep -rln "OFFBOARDED" src --include=*.ts
  src/modules/admin/admin.service.ts   (another status-flip site)
  src/platform/v1/tenant-export-offboarding.service.ts

No cron, worker, queue processor, or any other code anywhere in this
repository reacts to a tenant's status becoming OFFBOARDED. The
"deletion certificate" is a cryptographically signed artefact
asserting a fact - deletion occurred - that is simply false. This
directly and severely violates G-4's own wording: "Verified by
rehearsal, not by clause." Nothing here was verified by rehearsal;
it was asserted and signed as though it had been. Of every
fabrication defect found this session (D090, D098, D108, D110, D118,
D125), this is the most consequential: a signed artefact intended to
carry legal/regulatory weight, certifying something false.

A sibling method, TenantLifecycleService.offboardTenant() (a
different, separate implementation in tenant-lifecycle.service.ts),
was checked for comparison and found honest by design: it sets
status to "OFFBOARDING" (not "OFFBOARDED"), computes a future
`autoPurgeDate` (retentionDays out), and issues NO certificate at
all - it is explicitly a scheduling step, not a completion claim.
That method was NOT touched; only the fabricating one was.

MECHANISM (this phase's fix)
====================================
A full cascading purge across this platform's confirmed ~1000+
tenant-scoped tables is out of scope for a single pass - attempting
a partial, ad hoc delete here risked introducing new correctness bugs
(orphaned foreign keys, partial deletes masquerading as complete)
without actually closing the gap. The honest, tractable fix: stop the
signed artefact from claiming something unverified.

Renamed the artefact from "DELETION_CERTIFICATE" to
"OFFBOARDING_RECEIPT." It now accurately describes only what actually
happened in the transaction (status change, subscription
cancellation, export queued), explicitly sets `dataDeleted: false`,
and includes a `dataRetentionNote` stating plainly that tenant data
has not been deleted and that a real deletion certificate will only
be issued once deletion has actually occurred and been verified.

WHAT THIS PHASE DOES NOT COVER — the honest, load-bearing gap
===================================================================
Filed as D126 (CRITICAL). Not fixed in this pass:
  - No real tenant-data deletion mechanism exists anywhere in this
    codebase. "A tenant exits fully unaided and receives a deletion
    certificate" remains genuinely unmet - there is now an honest
    receipt instead of a false certificate, but no path to an actual,
    verified deletion certificate exists yet. Building one requires a
    real cascading-purge mechanism across this platform's ~1000+
    tenant-scoped tables (or a documented, narrower "regulated data"
    subset), plus a verification step (row-count-zero confirmation,
    analogous to this session's own J25 rehearsal-verification
    pattern) before a genuine DELETION_CERTIFICATE could honestly be
    issued.
  - `startExport()`'s DataExportJob rows are created with status
    'PENDING'/'PROCESSING' but confirmed, via the same grep sweep, to
    have no worker anywhere that ever processes them to completion -
    "complete export" (the deliverable's other named requirement) may
    itself be equally unfulfilled, not independently verified in this
    pass.
  - "Assisted migration away" (the deliverable's third named
    requirement) was not investigated at all.
