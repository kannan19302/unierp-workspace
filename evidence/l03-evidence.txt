L03 — Silent-catch and error-handling gate
Exit criterion: "An empty or swallowing catch fails CI. Every caught
error is either handled, wrapped with its cause, or re-thrown —
verified by breaking one."

BEFORE
======
No error-handling rules existed in unierp-api's eslint.config.mjs
(only L02's naming-convention rule, added this session, existed
before this phase).

MECHANISM
=========
Two real custom ESLint rules added to eslint.config.mjs, encoding
CODE_STANDARDS § 6.1 exactly:

  code-standards/no-swallowed-catch — a catch block with a non-empty
  body (no-empty already covers the empty case) that never references
  its caught error parameter anywhere in the block is flagged. This is
  a conservative, syntax-only proxy for "does something with the
  error" (handles, wraps, logs, rethrows) — a block that never even
  MENTIONS the parameter has discarded the evidence, exactly what
  § 6.1 forbids ("silently destroys the evidence").

  code-standards/no-cause-loss-rethrow — a `throw` statement inside a
  catch block that constructs a NEW error (not `throw err;` itself)
  without passing the original as a `{ cause }` option is flagged.
  Matches § 6.1's second named example exactly ("loses the cause and
  the stack").

Plus the built-in `no-empty` rule (`allowEmptyCatch: false`) for the
literal `catch {}` case named in the deliverable.

SPLIT CONFIG — a real, load-bearing architecture decision
===============================================================
These 3 rules are syntax-only (no type information needed), unlike
L02's boolean-naming rule. Initially merged into L02's existing single
config block, a full-repo scan OOM'd — even with L02's own rule
explicitly disabled via a CLI `--rule` override. This proved the OOM
came from `projectService: true` itself (which builds a full
TypeScript type program per matched file) rather than from any
specific rule being active. Fixed by splitting eslint.config.mjs into
two blocks: a broad one with plain parserOptions (no type info) for
L03's rules, and a narrower one (scoped to `src/modules/admin/*.ts`
only, matching L02's own already-narrow scope) carrying
`projectService: true` for L02's rule specifically.

PROOF — every named case verified against synthetic code first
====================================================================
Before trusting the rules against real code, verified all 4 named
shapes with a synthetic test file:

  function a() { try {...} catch (err) { console.log("failed"); } }
    -> flagged: "catch block never references its caught error
       parameter" (swallowed)
  function b() { try {...} catch (err) { throw new Error("failed"); } }
    -> flagged: "rethrow ... must pass the original error as
       { cause } ... losing 'err'"
  function c() { try {...} catch (err) { throw new Error("failed",
       { cause: err }); } }
    -> NOT flagged (correct: cause preserved)
  function d() { try {...} catch (err) { throw err; } }
    -> NOT flagged (correct: bare rethrow preserves everything)

All 4 outcomes matched the rule's stated intent exactly before the
synthetic file was deleted and a real full-repo scan was run.

WHAT THIS PHASE DOES NOT COVER
=================================
- The 22 real violations found were NOT fixed in this pass — this
  phase's own scope is building the working gate and baseline
  (matching L02/L06/L11/L14's own precedent), not fixing every
  pre-existing violation.
- The "references the parameter" heuristic for no-swallowed-catch is
  conservative and syntax-only: a catch block that references the
  parameter merely to check its type/message but still effectively
  discards it (e.g. `if (err instanceof Foo) {}`) would not be
  flagged — stated as a known limitation, not claimed exhaustive.
